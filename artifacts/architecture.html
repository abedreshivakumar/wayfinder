00Decisions locked for v0.1

Four calls made before any code, and what each one trades away on purpose.

Scope

Structure + data flow together

Both layers ship in the same first version, not phased. Higher risk of a longer stretch before anything is demoable, in exchange for the differentiated feature existing from day one.

LSP client

Hand-written, raw JSON-RPC

No client library. You write the stdio framing and request/response handling directly — full visibility into what pyright is actually returning when something looks wrong.

Input

Single file, exact file:line:col

No symbol search, no workspace scan. You supply the position by hand. Whole-repo, search-by-name resolution is deferred past v0.1.

Persistence

None — recompute every request

No SQLite, no cache. Every call re-runs the LSP + AST passes from scratch. Simplest possible backend; revisit only once it's actually slow.

02How one edge gets its data-flow label

The part that makes this different from a plain call graph. For every call site the AST pass finds, it reads the actual argument expression and the variable the return value is assigned to — then asks pyright for the inferred type at that exact position. If the same variable reappears as an argument two calls later, the edges are threaded, so a value's path is visible, not just the function path.

03Components

Four layers. Only one of them is a model call — kept out of the MVP entirely for now.

Layer 1 · Structure

LSP driver

Owns the pyright-langserver --stdio subprocess and the JSON-RPC framing. Exposes prepareCallHierarchy, incomingCalls, outgoingCalls as plain async functions.

Layer 2 · Data flow

AST + type pass

Walks each call site with Python's ast module, resolves argument/return types via textDocument/hover, threads reused variable names across hops.

Layer 3 · Assembly

Graph merge

Merges both passes into graph.json in memory. No persistence in v0.1 — every request recomputes from scratch; add a cache only once that's actually slow.

Layer 4 · Interface

React Flow canvas

Expandable node graph. Click a node → fetch its neighbors; edge labels show the threaded type; no LLM narration in v0.1.

04Build order

Riskiest, least-glamorous piece first. If pyright can't produce a correct graph, nothing downstream matters.

  1. LSP driver, proven on one real symbol

    Spawn pyright-langserver, complete the initialize handshake, open one file, call prepareCallHierarchy at a known line:col, print the raw result.

    de-risks: can we even talk to pyright reliably

  2. BFS expansion → graph.json

    Walk incoming/outgoing calls 2 hops out from that symbol, dedupe by (file, range), write the node/edge JSON. Validate it by hand against the real source.

    de-risks: is the graph actually correct, not just non-empty

  3. AST + hover data-flow labels

    For each edge already in the graph, extract the call-site argument expressions and resolve their types. Thread repeated variable names across edges.

    de-risks: the actual differentiator — everything above this is table stakes

  4. FastAPI wrapper

    One route, GET /graph?file=&line=&col=, that runs steps 1–3 fresh on every call and returns the JSON. No auth, no cache, no symbol search — one file, one exact position, one process.

  5. React Flow canvas

    Render the JSON, click-to-expand, edge labels visible. This is the first point the tool is usable by someone other than you.
