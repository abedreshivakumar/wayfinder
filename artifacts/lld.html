Part 1

Static Engine

owns: talking to pyright, building the raw call graph, labeling edges with data flow

The deterministic core. Everything else in the system depends on this being correct — it's the only part with zero tolerance for "close enough."

File layout

  • lsp/client.py — raw JSON-RPC over stdio, message framing
  • lsp/pyright_driver.py — handshake + typed call-hierarchy/hover methods
  • lsp/position.py — AST ↔ LSP position conversion (the one place this math lives)
  • graph/builder.py — BFS expansion into a Graph object
  • dataflow/ast_pass.py — call-site + assignment extraction via ast.NodeVisitor
  • dataflow/type_resolver.py — hover request → parsed type string
  • dataflow/thread.py — links a reused variable name across edges

Key signatures

class LSPClient:
    def start(self, command: list[str]) -> None: # spawn subprocess
    def request(self, method: str, params: dict) -> dict: # blocking, framed
    def notify(self, method: str, params: dict) -> None: ...
    def shutdown(self) -> None: ...

class PyrightDriver:
    def __init__(self, client: LSPClient, repo_root: str): ...
    def initialize(self) -> None: # initialize -> initialized handshake
    def open_file(self, file: str) -> None: # textDocument/didOpen
    def prepare_call_hierarchy(self, file: str, line: int, col: int) -> CallHierarchyItem: ...
    def incoming_calls(self, item: CallHierarchyItem) -> list[IncomingCall]: ...
    def outgoing_calls(self, item: CallHierarchyItem) -> list[OutgoingCall]: ...
    def hover(self, file: str, line: int, col: int) -> str | None: # raw markdown

def build_call_graph(driver: PyrightDriver, start: Position, hops: int = 2) -> Graph: ...

class CallSiteVisitor(ast.NodeVisitor):
    def visit_Call(self, node: ast.Call) -> None: # records CallSite
    def visit_Assign(self, node: ast.Assign) -> None: # tracks assigned var for prior call

def resolve_type(driver: PyrightDriver, file: str, line: int, col: int) -> str | None: ...
def thread_variables(sites: list[CallSite]) -> dict[str, list[CallSite]]: ...
Output contract → Part 2
One Graph object: {nodes: list[Node], edges: list[Edge]}, matching the data-model fields already locked (id/name/kind/file/range/language on nodes; from/to/direction/args/returns on edges). Part 2 never talks to pyright — it only ever receives this object.
Known limitation, by design
Cannot see dynamic dispatch, monkey-patching, or callback registries — that gap is intentionally Part 3's Flow-Tracer's job, not this part's. Don't try to patch this in here.
Part 2

Graph Store

owns: persistence, the one query interface everything else reads through

SQLite (D1). This is the single choke point both the API and the MCP server query — neither owns the data, both go through GraphRepository.

Schema

CREATE TABLE nodes (
  id            TEXT PRIMARY KEY,
  repo          TEXT NOT NULL,
  commit_sha    TEXT NOT NULL,
  name          TEXT NOT NULL,
  kind          TEXT NOT NULL,          -- function | method | class
  file          TEXT NOT NULL,
  start_line    INTEGER, start_col INTEGER,
  end_line      INTEGER, end_col INTEGER,
  language      TEXT NOT NULL,
  narration     TEXT,                   -- NULL until Narrator runs
  narrated_at   TIMESTAMP
);

CREATE TABLE edges (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  repo              TEXT NOT NULL,
  commit_sha        TEXT NOT NULL,
  from_id           TEXT NOT NULL REFERENCES nodes(id),
  to_id             TEXT NOT NULL REFERENCES nodes(id),
  direction         TEXT NOT NULL,      -- incoming | outgoing
  args_json         TEXT,               -- [{name, type}]
  returns_json      TEXT,               -- {var, type}
  runtime_confirmed BOOLEAN DEFAULT 0
);

CREATE TABLE drift_flags (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  node_id     TEXT NOT NULL REFERENCES nodes(id),
  detail      TEXT NOT NULL,
  detected_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_edges_from ON edges(from_id);
CREATE INDEX idx_edges_to   ON edges(to_id);

Key signatures

class GraphRepository:
    def __init__(self, db_path: str): ...
    def upsert_graph(self, graph: Graph, repo: str, commit: str) -> None: ...
    def get_neighbors(self, node_id: str, hops: int, direction: str | None = None) -> Graph: ...
    def get_node(self, node_id: str) -> Node | None: ...
    def set_narration(self, node_id: str, text: str) -> None: ...
    def add_drift_flag(self, node_id: str, detail: str) -> None: ...
    def mark_runtime_confirmed(self, from_id: str, to_id: str) -> None: ...
Interface contract
GraphRepository is the only way anything (API, MCP server, background Drift-Checker job) touches SQLite. No other module opens the .db file directly — this is what keeps the MCP server a thin adapter instead of a second implementation of graph queries.
Part 3

Agent Layer

owns: everything that calls a model — the Orchestrator plus four specialists

Built on the Claude Agent SDK (D2). Every specialist is grounded on real source text pulled from GraphRepository — none of them are ever handed "the whole repo" or asked to reason from memory.

File layout

  • agents/orchestrator.py — the one true multi-step agent, tool-calling loop via Claude Agent SDK
  • agents/narrator.py — one node in, one explanation out
  • agents/path_explainer.py — a resolved path in, one narrated story out
  • agents/flow_tracer.py — run trace (deterministic) + reconcile (model)
  • agents/drift_checker.py — background job, one node at a time

Key signatures

class Orchestrator:
    # registered tools, exposed to the SDK's tool-calling loop:
    def resolve_symbol(self, query: str) -> Position: ...
    def get_graph(self, position: Position, hops: int) -> Graph: ...
    def call_narrator(self, node_id: str) -> str: ...
    def call_path_explainer(self, node_ids: list[str]) -> str: ...
    def call_flow_tracer(self, entry_point: str) -> Graph: ...
    def answer(self, question: str) -> str: # entry point, drives the loop

def narrate_node(node: Node, source: str) -> str: # single grounded call
def explain_path(nodes: list[Node], edges: list[Edge]) -> str: ...

class FlowTracer:
    def run_trace(self, entry_point: str, sample_input: dict) -> RawTrace: # sys.settrace, deterministic
    def reconcile(self, trace: RawTrace, graph: Graph) -> list[Edge]: # model step

def check_node(node: Node, docstring: str, graph: Graph) -> list[DriftFlag]: ...
Grounding rule, applies to all five
Every prompt in this layer includes the actual source snippet or graph slice as context — never a bare question with no data attached. This is the difference between "narration" and "hallucination" and it's non-negotiable across every agent here.
Part 4

API + MCP Interface

owns: the two front doors onto the graph store — HTTP for the web app, MCP for other agents

Both are thin. Neither contains graph logic of its own — that all lives in Parts 1–3, reached through GraphRepository.

File layout

  • api/main.py — FastAPI app, lifespan-managed PyrightDriver
  • api/routes.py — the three HTTP routes
  • mcp/server.py — MCP tool definitions, in-process calls to the same repository/agents

HTTP routes

RouteBehavior
GET /graph?file=&line=&col=&hops=2 → runs Part 1 fresh (no cache, per D-locked MVP scope), returns Graph JSON
POST /narrate{node_id} → cached narration if present, else calls Narrator and stores it
POST /ask{question} → hands off to Orchestrator.answer(), streamed response

MCP tools exposed

ToolMaps to
who_callsGraphRepository.get_neighbors(direction="incoming")
what_does_this_callGraphRepository.get_neighbors(direction="outgoing")
explain_functionnarrate_node(...)
trace_pathOrchestrator.call_path_explainer(...)
Lifecycle detail
The pyright subprocess is started once in FastAPI's lifespan, not per request — both the HTTP route and the MCP server share the same running PyrightDriver instance, never spawn their own.
Part 5

Frontend

owns: the only part a human looks at

React Flow. No graph logic here either — it renders whatever /graph and /ask return.

File layout

  • src/App.tsx — top-level state: current position, graph data, question box
  • src/hooks/useGraph.ts — fetches /graph, re-fetches on node click
  • src/layout.ts — dagre auto-layout, since LSP gives no x/y
  • src/components/NodeCard.tsx — renders a node, lazy-loads narration on click
  • src/components/DataFlowEdge.tsx — custom edge, renders the var: Type label
  • src/components/QuestionBox.tsx — free-text question → /ask

Key signatures

function useGraph(position: Position, hops: number): {
  nodes: Node[]; edges: Edge[]; loading: boolean; refetch: (p: Position) => void
}

function computeLayout(nodes: Node[], edges: Edge[]): PositionedNode[] // dagre, left-to-right

function NodeCard({ node, onExpand }: { node: Node; onExpand: (id: string) => void })

function DataFlowEdge({ data }: { data: { arg?: string; type?: string } })
Rendering contract
Narration is fetched lazily, per node, only on click — the initial /graph response never blocks on any agent call. Structure renders instantly; explanation appears a beat later. This is the same "deterministic first, judgment on top" split as the backend, expressed in the UI's loading behavior.
