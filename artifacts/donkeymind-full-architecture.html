02Agent layer detail

Only the Orchestrator is a real multi-step agent — it decides which of the other four to call and when to stop. The other four are single, tightly-grounded calls; calling them "agents" is convenient but each is really one typed function that happens to invoke a model once (Flow-Tracer is the exception: run trace → interpret → reconcile is inherently two steps).

Lead agent

Orchestrator

Owns the tool-calling loop. Resolves the user's question to a starting symbol, decides hop depth, picks which specialist(s) to invoke, and when it has enough to answer. Built on the Claude Agent SDK — no hand-rolled loop, kept cost-minimal.

Specialist

Narrator

One function's real source in, one/three-sentence explanation out. No graph traversal of its own.

Specialist

Path-Explainer

A resolved multi-hop path in, a narrated walkthrough out. Reasons across several nodes' purposes together.

Specialist · 2 steps

Flow-Tracer

Runs or replays a trace for one entry point, then reconciles it against the static graph — the only place dynamic dispatch and monkey-patching become visible.

Specialist · background

Drift-Checker

Runs opportunistically over nodes that have existing docstrings/comments, flags where they contradict what the graph shows.

04Language rollout

The static engine is built against the LSP protocol, not against Python specifically — call hierarchy is a standard LSP capability every serious language server implements. Python first because it's your strength and it's what proves the pattern; each language after that is "swap the language server," not "rewrite the engine."

06MCP interface

A thin adapter over the same graph-store query layer the FastAPI backend already uses — not a second engine, just a second way in. This is what turns Donkeymind from an app you open into a tool Claude Code (or any MCP client) can call mid-task.
