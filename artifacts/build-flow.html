02Phases

Each phase has one exit criterion. Don't start the next phase until the current one's exit criterion is actually true — not "probably works," actually observed.

Phase 1

LSP handshake, proven on one real symbol

Talk to pyright directly and get one real CallHierarchyItem back. This is pure protocol plumbing — no graph logic yet.

Read first

  • LSP spec — Base Protocol (framing)
  • LSP spec — Call Hierarchy section
  • pyright README + import-resolution doc

Build

  • Spawn pyright-langserver --stdio
  • initialize → initialized → didOpen
  • prepareCallHierarchy at a known position

Exit check: raw JSON printed to the terminal shows a correct CallHierarchyItem (right name, right file, right range) for a function you picked by hand.

Phase 2

BFS expansion → graph.json

Turn one item into a graph. Still no data flow — structure only.

Read first

  • Nothing new — same LSP spec section, now incomingCalls/outgoingCalls

Build

  • Walk incoming + outgoing calls, 2 hops out
  • Dedupe nodes by (file, range)
  • Emit {nodes: [...], edges: [...]}

Exit check: you read the emitted JSON against the real source file by eye and every edge is a call that's actually there — no missing calls, no fabricated ones.

Phase 3

AST + hover data-flow labels

The differentiator. For every edge already in the graph, label it with what argument/return value threads through it.

Read first

  • ast module docs — NodeVisitor, the ASDL grammar table
  • LSP spec — textDocument/hover (shape only; fire a real request and read the raw text before assuming structure)

Build

  • Write one AST line/col ↔ LSP position converter, use it everywhere
  • Walk each call site, capture assigned variable + args
  • Hover each position, parse the type out of the markdown
  • Thread repeated variable names across hops

Exit check: at least one edge in the graph shows a correct var: Type label that matches what the source actually does, on a real (not toy) function.

Phase 4

FastAPI wrapper

Make phases 1–3 reachable over HTTP. No new logic — just an entry point.

Read first

  • FastAPI — Lifespan Events (subprocess must not spawn per-request)
  • asyncio subprocess docs

Build

  • pyright subprocess started once, in lifespan
  • GET /graph?file=&line=&col=
  • Runs phases 1–3 fresh every call, returns JSON

Exit check: curl against the running server returns the same correct graph you validated by hand in Phase 3.

Phase 5

React Flow canvas

First point the tool is usable by someone who isn't reading raw JSON.

Read first

  • xyflow.com/learn — Layouting (dagre/ELK, since LSP gives no positions)
  • xyflow.com — Custom Edges (for the type labels)

Build

  • Fetch the graph, auto-layout with dagre
  • Render nodes + labeled edges
  • Click a node → re-fetch centered on it

Exit check: someone other than you can open the page, click through a real function's call graph, and read the data-flow labels without you narrating it.

03Definition of done for v0.1

The whole MVP, stated as one scenario. If this works end to end, v0.1 is complete — nothing more is required before moving to the agent layer.

  • You paste a real file:line:col from an unfamiliar Python codebase into the running app.
  • Within a few seconds, a graph renders showing that function's real callers and callees, 2 hops out.
  • At least the direct edges show a correct data-flow label — what gets passed, as what type.
  • Clicking a neighboring node re-centers the graph on it, without a page reload.
  • Every edge shown is independently verifiable against the real source — nothing on screen came from a model guess.
